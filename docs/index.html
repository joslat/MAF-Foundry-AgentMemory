Microsoft Agent Framework · Microsoft Foundry · AgentMemory for .NET

Agents in the cloud.
Memory on my laptop.

Three agents run in Microsoft Foundry. Their memory is a Neo4j knowledge graph on this PC, reached through an authenticated Dev Tunnel and the Model Context Protocol. A new conversation, in any of the three, can recall what another one saved.

How it works

One shared foundation under all three demos. Memory never leaves the PC; Foundry only ever sees tool results.

Neo4j

Holds the memory as a graph: preferences, facts, entities and messages, each with provenance and a read-audit trail. Runs in Docker, bound to 127.0.0.1 only.

AgentMemory MCP host

Exposes the graph as MCP tools over HTTP on port 5233. Every call is pinned to one owner, foundry-demo, so the model cannot pick or switch identities.

Dev Tunnel

Publishes that one port as an HTTPS URL that only accepts requests carrying the connect token. Nothing else on the PC is reachable.

Demo 1 · simplest

Prompt Agent + local MCP

Idea. A no-code Foundry agent whose memory is a server on my laptop.

How. The agent is a Foundry resource: a model, a block of instructions and a remote MCP tool pointing at the tunnel URL with the token header. When the model decides to call a memory tool, Foundry's tool runner opens an MCP session through the tunnel, forwards the call and hands the JSON back to the model.

Who decides to recall or remember. The model. The instructions teach it when to call memory_search, how to phrase a specific query, how to read the result, and when to save with memory_add_preference or memory_add_fact.

Where it lives. In the portal: Build → Agents → prompt-agent. Its definition is recorded in scenarios/02-prompt-agent/README.md.

Demo 2 · my own code

Hosted MAF agent in C#, model-selected tool

Idea. The same memory, from a C# process deployed to Foundry as a Hosted Agent.

How. An ASP.NET process built with the Microsoft Agent Framework runs inside Foundry, deployed from source with azd. Foundry talks to it over the Responses protocol. At startup it opens its own MCP client to the tunnel and exposes exactly one function to the model, memory_search. The MCP connection belongs to the application; nothing is configured in the portal.

Where it lives. src/hosted-mcp-tools/Program.cs: the connection (line 34), the tool (46–66), the agent (74–90), the hosting (93–96). MemoryConnection.cs reconnects and retries once if the host on the PC was restarted.

The agent, in code

List<AITool> tools =
  [AIFunctionFactory.Create(MemorySearch, name: "memory_search")];

AIAgent agent = new AIProjectClient(projectEndpoint, credential)
  .AsAIAgent(model: deployment,
             instructions: "...call memory_search first...",
             name: "hosted-mcp-tools",
             tools: tools);

builder.Services.AddFoundryResponses(agent);
app.MapFoundryResponses();

Demo 3 · automatic

Hosted MAF agent with an AIContextProvider

Idea. The model has no memory tool. Recall is a property of the agent.

How. Same hosting and connection as demo 2, but the agent carries an AIContextProvider. The agent framework calls it before every model call: it takes the last user message, runs memory_search itself, keeps the preferences and facts, bounds the size, and injects them as a reference message marked as untrusted data. There is no tool for the model to choose or skip.

Where it lives. src/hosted-memory-context/Program.cs (the agent, lines 47–63) and RemoteMemoryContextProvider.cs (one method, ProvideAIContextAsync).

The provider, in code

protected override async ValueTask<AIContext> ProvideAIContextAsync(
    InvokingContext context, CancellationToken ct)
{
  var query = /* last user message */;
  var result = await memory.CallToolAsync("memory_search",
      new() { ["query"] = query, ["maxResults"] = 3 }, ct);
  var items = /* preferences + facts, bounded */;
  return new AIContext { Messages =
    [new ChatMessage(ChatRole.User,
       "" + items + "")] };
}

Setup

What runs where, and how to bring it up. Full detail in README.md and DEMO-GUIDE.md.

  1. Neo4j in Dockerdocker compose -f local-memory/docker-compose.yml up -d · ports on 127.0.0.1 only · browser at localhost:7474
  2. AgentMemory MCP host.\local-memory\run-mcp.ps1 · installs as dotnet tool install -g AgentMemory.McpHost · owner pinned to foundry-demo · configured by local-memory/.env (Azure OpenAI for embeddings, Neo4j password)
  3. Seed and verify, no model involvedcd src/memory-seed-check; dotnet run -- seed; dotnet run -- check
  4. Dev Tunneldevtunnel create agentmemory-demo; devtunnel port create -p 5233 --protocol http; devtunnel token --scopes connect; devtunnel host agentmemory-demo · the tunnel lives 30 days, a connect token about 24 hours
  5. Prove recall through the public URLdotnet run -- check with MEMORY_MCP_URL set to the tunnel root and MEMORY_TUNNEL_TOKEN to the token
  6. Demo 1 in the portal prompt-agent → Tools → MCP: server label agentmemory, the tunnel root URL, header X-Tunnel-Authorization: tunnel <token> stored in a project connection, allowed tools memory_search, memory_add_preference, memory_add_fact, plus the instructions from the scenario README
  7. Demos 2 and 3 with azdazd env set MEMORY_MCP_URL ...; azd env set MEMORY_TUNNEL_TOKEN ...; azd provision --preview; azd provision; azd deploy in each src/hosted-* folder · the preview must say "Using existing Foundry project; nothing to provision"

The MCP host has no authentication of its own; the tunnel token is the boundary. Only port 5233 is published, Neo4j never is, and the hosted C# agents expose no write tool. Stop the tunnel after the talk.
